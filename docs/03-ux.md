# 03. Intefejs i wymaganie niefunkcjonalne

Dokument zawiera makiety widoków (wireframe'y), zasady spójności interfejsu oraz wymagania niefunkcjonalne.
Interfejs jest z założenia **renderowany po stronie serwera**, 
z wyjątkiem zasobów tożsamości (użytkownika, organizacji), lub projektu, mających własne zasoby frontendu.
Funkcjonalność dla użytkownika końcowego, dostępna z CLI i API (zob. [05-architecture.md](05-architecture.md)),
jest również dostępna z poziomu przeglądarki po autoryzacji sesji.

## Mapa widoków

| Widok | Adres | Do czego służy |
| ----- | ----- | -------------- |
| **Odkrywaj** | `/` | Obrazy, nagrania, projekty, osoby i kolektywy. |
| Obrazy | `/?view=images` | Lista prac graficznych. |
| Nagrania | `/?view=audio` | Lista nagrań. |
| Projekty | `/?view=projects` | Katalog projektów publicznych tożsamości. |
| Osoby i kolektywy | `/?view=people` | Publiczny katalog tożsamości. |
| **Profil** | `/i/:ref` | Opis, zdjęcie, projekty, prace, klucze i historia. |
| **Projekt** | `/i/:ref/projects/:project_id` | Opis projektu i jego materiały. |
| **Dołącz** | `/join` | Utworzenie osoby lub kolektywu. |
| **Odblokuj klucze** | `/login` | Odblokowanie lub przywrócenie lokalnego skarbca. |
| **Pracownia** | `/studio` | Przeglądanie i podpisywanie zmian. |

## Proces UX

### Część publiczna

Najpierw zaprojektowaliśmy cztery główne widoki: 
**Odkrywaj, profil osoby, profil kolektywu i stronę projektu**. 
Sprawdzaliśmy je na komputerze.

Z tej części do aplikacji trafiły:

- widoczny podział na obrazy, nagrania, projekty i katalog osób;
- osobne karty projektów, również na profilu właściciela;
- proste przejście od projektu do profilu oraz do Pracowni;
- informacja o tym, że `unlisted` nie oznacza prywatnej strony;
- komunikaty dla pustego profilu, braku publikacji i brakujących bajtów pliku;
- schowanie technicznych szczegółów pod rozwijanymi sekcjami.

Projekt należy do tożsamości. Nie pokazujemy listy „członków kolektywu” na podstawie samych grantów, bo uprawnienia kluczy nie są formalnym członkostwem.

### Pracownia

Drugi etap dotyczył tego, **jak pracować na zawartości profilu**, nie mieszając jej z wyborem klucza.

Pracownia ma siedem sekcji:

| Sekcja | Co pokazuje |
| --- | --- |
| **Przegląd** | Krótkie podsumowanie wybranej przestrzeni. |
| **Profil** | Nazwa wyświetlana, opis, miejsce, strona internetowa i zdjęcie. |
| **Projekty** | Projekty danej tożsamości i ich ustawienia. |
| **Zasoby** | Obrazy, nagrania i pliki strony; wyszukiwanie, filtry, edycja i przenoszenie. |
| **Współpraca** | Granty, zakresy uprawnień, delegacje i cofanie dostępu. |
| **Klucze** | Informacje o kluczach, lokalny skarbiec i klucz do sesji przesyłania plików. |
| **Historia** | Zmiany w dzienniku oraz ich szczegóły techniczne. |

Na dużym ekranie sekcje są w nawigacji bocznej, a na małym w menu. U góry widać **wybraną tożsamość**, **aktywny klucz** i — gdy dotyczy — **projekt**.

Rozróżniliśmy trzy zakresy przeglądania zasobów:

- **Cała tożsamość:** pliki ze wszystkich projektów i z przestrzeni głównej.
- **Przestrzeń główna:** pliki bez projektu.
- **Wybrany projekt:** pliki jednego projektu.

Tożsamość nie zmienia się automatycznie po wybraniu innego klucza. **Odblokowanie skarbca nie jest logowaniem do serwera.** Osoba bez klucza nadal może otworzyć Pracownię w trybie odczytu.

### Formularze i podpisy

W trzecim etapie skupiliśmy się na chwilach, w których użytkownik może coś stracić albo zrobić przypadkowo.

W obecnym frontendzie:

1. **Najpierw przygotowuje się szkic**: profil, projekt, grant lub plik.
2. **Przed podpisaniem widać podsumowanie**: co, gdzie i którym kluczem ma zostać zmienione. Szczegóły techniczne można rozwinąć.
3. **Anulowanie nie publikuje operacji.** Samo odblokowanie klucza też niczego nie podpisuje.
4. **Przy konflikcie dziennika** użytkownik odczytuje aktualny stan i ponownie zatwierdza zmianę. Program nie podpisuje jej sam jeszcze raz.
5. **Przy nieznanym wyniku zapisu** można sprawdzić tę samą operację po jej ID, zamiast przygotowywać od razu nową.

Do tego dochodzą osobne etapy przy tworzeniu tożsamości: 
zabezpieczenie skarbca, potwierdzenie kopii i dopiero potem podpisanie `genesis`. 
Przy przywracaniu kopii jest ostrzeżenie przed zastąpieniem istniejącego skarbca.

**Ważne ograniczenie:** 
szkice i nierozstrzygnięte próby nie są trwałym systemem przechowywania roboczych zmian. Odświeżenie lub zamknięcie karty może je usunąć.

## Zasady spójności interfejsu

1. **Jedna rama dla wszystkich stron.** 
    Nagłówek, treść i stopka pochodzą ze wspólnego komponentu `Layouts.shell`; 
    strony błędów używają tej samej ramy.
2. **Jeden zestaw tokenów, wiele palet.**
    Kolory, odstępy i krój są zmiennymi CSS (`:root`);
    nic nie jest kodowane na sztywno w komponentach.
    Każda tożsamość może mieć przypisaną własną paletę kolorów, to dotyczy wizytówek profilu, stron projektów, lokalnych zasobów.
    Widoki główne i niezależne od tożsamości używają jednej, głównej palety kolorów.
    Nawigacja po wszystkich stronach powinna obejmować nakładkę instancji platformy oraz autoryzowanej sesji.
3. **Znaczenie grantów niezależne od koloru.**
    Stan uprawnienia ma zawsze etykietę tekstową, a typ węzła w dzienniku różni się wypełnieniem, nie tylko renderowaną barwą.
4. **Identyfikatory zawsze w tej samej formie.**
    Długie identyfikatory (klucze, zdarzenia, tożsamości) są skracane do postaci `abcdef...wxyz` czcionką stałej szerokości,
    a pełna wartość jest w atrybucie `title` lub w tablicy danych.
    Klucz jest pokazywany jako odnośnik do tożsamości, której jest "domem", jeśli serwer ją zna.
5. **Daty i liczby po polsku.**
    Jeden komponent formatuje czas w UTC (np. "12 października 2026, 12:00 UTC" z `<time datetime>`),
    a jedna funkcja odmienia liczebniki ("1 zdarzenie", "2 zdarzenia", "5 zdarzeń").
6. **Język interfejsu to polski**;
    identyfikatory techniczne (nazwy akcji, kody błędów API) pozostają po angielsku i są pisane czcionką stałej szerokości.
7. **Wzorzec błędu.**
    Błąd oznacza się kolorem ostrzegawczym, tekstem opisującym problem i, jeśli trzeba, `role="alert"`; nigdy samym kolorem.
8. **Stany puste mówią, co zrobić dalej** (katalog bez tożsamości pokazuje polecenia CLI).
9. **Zapisujące interakcje** wyglądają tak samo:
    pola formularza z limitem znaków, lista zmienionych pól, załączniki dla zasobów, lista zmienionych pól, 
    lokalne wyrenderowanie zmian przed ich podpisaniem (planowane), 
    możliwość zapisania postępujących zmian jako lokalny diff dziennika (planowane),
    jeden przycisk akcji głównej (złożenia podpisu) i "Anuluj".

## Wymagania niefunkcjonalne

### Bezpieczeństwo

| Wymaganie | Realizacja |
| --------- | ---------- |
| Autentyczność zmian | każde zdarzenie podpisane Ed25519; domeny podpisów oddzielone prefiksami (`oktavarium/event/v1`, `oktavarium/login/v1`, `oktavarium/event-id/v1`) |
| Integralność historii | łańcuch `prev`, unikalny `(identity_id, seq)`, surowe bajty ładunku, weryfikacja od zera (`Log.verify`) |
| Serwer nie ufa klientowi | czas ważności grantów według zegara serwera; reguły (zakres, zawężanie, łańcuch) sprawdzane po stronie serwera |
| Ochrona stron przed wstrzyknięciem treści | 
    nagłówek `Content-Security-Policy: default-src 'self'; img-src 'self' data:; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`; 
    brak skryptów i stylów inline; treści profilu escapowane przez HEEx; odnośniki tylko do `http(s)` |
| Limit rozmiaru żądania | parser JSON przyjmuje do 64 KiB (koperta ma kilkaset bajtów) |
| Klucze prywatne nie opuszczają komputera użytkownika | pliki 0600, zapis bez nadpisywania; serwer nigdy nie widzi klucza prywatnego |
| Ochrona przed nadużyciem API | ograniczanie liczby żądań |
| Ochrona plików kluczy | szyfrowanie hasłem (dziś jawny plik z uprawnieniami 0600) |
| Własny HTML/CSS/JS tożsamości lub projektu | jest serwowany z osobnego hosta, jeśli instancja ma skonfigurowaną domenę stron; nie jest uruchamiany wewnątrz widoków pracowni |

### Niezawodność i trwałość

| Wymaganie | Realizacja |
| --------- | ---------- |
| Zapis atomowy | zdarzenie i projekcja w jednej transakcji |
| Brak wyścigów przy zapisie do jednego dziennika | `BEGIN IMMEDIATE` w SQLite + unikalny indeks `(identity_id, seq)`; przegrany dostaje `bad_seq` |
| Odtwarzalność stanu | projekcję można sprawdzić i odbudować z dzienników (`mix oktavarium.rebuild`) |
| Kopie zapasowe | plik SQLite kopiowany przez operatora; procedura jeszcze nieopisana |

### Użyteczność i dostępność

| Wymaganie | Realizacja |
| --------- | ---------- |
| Strony główne działają bez JavaScriptu | renderowanie po stronie serwera, brak skryptów z wyjątkiem subdomen tożsamości (jeśli takie skrypty posiadają) |
| Układ responsywny | dwie kolumny od 60 rem, jedna kolumna poniżej; tabela uprawnień jako karty poniżej 44 rem |
| Nawigacja klawiaturą | odnośnik "przejdź do treści", widoczny wskaźnik ostrości (3px, kontrast w obu motywach) |
| Semantyka | `lang="pl"`, nagłówki h1-h3, `<main>`, tabela z `<caption>` i `scope`, listy dla dziennika i katalogu, `<time>` |
| Kontrast | policzony stosunek kontrastru (WCAG): jasny motyw - tekst podstawowy 14,6:1, drugorzędny 6,1:1, 
    odnośniki 7,7:1, komunikaty o błędzie 6,5:1; ciemny - odpowiednio 12,2:1, 6,4:1, 8,4:1, 8,2:1; 
    wszystkie pary z >= 6:1 (próg AA dla zwykłego tekstu to 4,5:1) |
| Motyw jasny i ciemny | `prefers-color-scheme`, `color-scheme: light dark` |
| Motyw własny subdomen | zasoby HTML/CSS/JS |
| Wydruk | styl `@media print` (biały papier, ukryta nawigacja) |

### Wydajność i skalowanie

| Wymaganie | Realizacja |
| --------- | ---------- |
| Płynne działanie dla małej, zamkniętej społeczności (setki użytkowników) | jeden węzeł, SQLite, dziennik stronicowany po 50 zdarzeń |
| Brak zewnętrznych zasobów na stronach | system fonts, brak CDN, brak zewnętrznych skryptów i czcionek |

### Utrzymanie i przenośność

| Wymaganie | Realizacja |
| --------- | ---------- |
| Proste samodzielne uruchomienie | jedna aplikacja Elixir i jeden plik bazy; `mix setup`, `mix phx.server` |
| Testowalność | rdzeń bez bazy (czyste funkcje) testowany osobno |
| Konfiguracja przez środowisko | `DATABASE_PATH`, `SECRET_KEY_BASE`, `PHX_HOST`, `PORT`, `POOL_SIZE`, `OKTAVARIUM_REGISTRATION`, `OKTAVARIUM_BLOB_DIR`, `OKTAVARIUM_SITES_DOMAIN` |
| Niezależność tożsamości od instancji | identyfikator tożsamości z hasha genesis, nie z bazy |
